## 이런 문제를 풉니다

> "10시 30분 치과 예약, 3시 30분 미팅. 그 사이에 은행 업무랑 서류 발급도 해야 하는데... 어디를 먼저 가야 안 늦을까?"

시간이 고정된 일정과 언제 해도 되는 일정이 섞이면 사람이 머리로 순서를 짜기 어렵습니다. 게다가 출발 시각을 잘못 계산하면 약속에 늦습니다.

이 앱은 세 가지를 자동으로 처리합니다.

| 문제 | 해결 |
|:---|:---|
| 일정 순서를 어떻게 짜야 이동이 최소인지 모르겠다 | 고정 일정 시각을 지키면서 유연 일정만 재배치 |
| 도착 시각이 물리적으로 불가능한지 미리 모르겠다 | 지연 분 단위로 **도착 불가 경고** 표시 |
| 여러 명이 모일 때 누군가만 멀리 온다 | 이동 시간 **분산이 최소인 중간지점** 계산 + 장소 추천 |

## 주요 기능

### 🗺️ 동선 최적화
고정형(`fixed`)과 유연형(`flexible`) 일정을 함께 계산합니다. 고정 일정의 시각과 순서는 절대 바뀌지 않고, 유연 일정만 이동 시간이 최소가 되는 자리로 삽입됩니다. 출발지에서 시작해 다시 출발지로 돌아오는 왕복 동선까지 포함합니다.

### ⚠️ 도착 불가 감지
이전 장소에서 아무리 빨리 출발해도 다음 고정 일정에 도착할 수 없는 조합을 찾아냅니다. 단순히 "불가능"이라고만 알리지 않고, 몇 분 늦는지와 그 이유를 함께 보여줍니다.

```
고정 일정 [파트너사 미팅](15:30)에 도착하려면 최소 14:50에 이전 장소에서 출발해야 하지만,
이동 시간(55분)으로 인해 15분 늦어집니다.
```

### 🤝 공평한 중간지점 계산
참여자들의 출발지를 받아 기하 중심점 주변을 격자 탐색하면서, **각자의 이동 시간 분산이 가장 작은 지점**을 찾습니다. 단순 중간 좌표가 아니라 "체감 이동 시간이 비슷해지는 곳"이 기준입니다. 계산된 지점 주변에서 카페 · 음식점 · 베이커리 · 펍을 검색해 실제 약속 장소 후보로 제안합니다.

### ⏰ 출발 알림
최적화 결과가 갱신될 때마다 각 구간의 출발 시각에 맞춰 알림이 예약됩니다.

```
출발 시각 = 목표 도착 시각 − 이동 시간 − 여유 시간
```

Service Worker를 통해 예약되므로 탭이 백그라운드에 있어도 동작합니다. 상단 배너에는 다음 출발 일정이 실시간으로 표시됩니다.

### 🚦 혼잡 시간 반영
출퇴근 시간대(08:00–09:30, 17:30–19:30)에는 혼잡 계수를 곱해 이동 시간을 보정합니다.

### 💾 브라우저 저장 & 날짜별 관리
일정은 `YYYY-MM-DD` 키로 날짜별로 관리되고 `localStorage`에 저장됩니다. 새로고침해도, 브라우저를 닫았다 열어도 그대로 남아 있습니다.

### 🎯 프리셋
주말 나들이형 / 업무 일정형 샘플을 한 번에 불러와 바로 동작을 확인할 수 있습니다.

## 핵심 알고리즘

### 1. 동선 최적화 — `src/utils/routeOptimizer.ts`

```
① 일정을 고정형 / 유연형으로 분리  
② 고정형만으로 실현 가능한지 먼저 검증 → 불가하면 경고 수집  
③ 유연형 순서 후보 생성  
     n ≤ 5  →  전체 순열 (최대 120가지)  
     n > 5  →  초기 해 + 2-opt 스왑 이웃 (최대 40가지)  
④ 각 후보를 고정 일정 슬롯 사이에 삽입해 전체 시퀀스 구성  
⑤ 시퀀스별 총 이동 시간 · 도착 가능성 평가 → 최적 해 선택  
⑥ 구간(RouteLeg) 단위로 출발/도착/체류 시각 확정  
```

이동 시간 조회 결과는 `from_to_mode` 키로 메모이제이션되어 같은 구간을 반복 계산하지 않습니다. 일정 10~15개 기준 **3초 이내** 완료를 목표로 설계했습니다.

### 2. 공평 중간지점 — `src/utils/midwayCalculator.ts`

```
① 참여자 출발지의 기하 중심점(centroid) 계산
② 중심점 주변 25개 후보 지점을 동심 격자로 생성
③ 각 후보에서 참여자별 이동 시간 산출
④ 이동 시간의 분산(variance)이 최소인 지점 선택
⑤ 표준편차 · 최대 시간 격차 · 계산 소요 시간 함께 반환
```

경계 케이스도 정의되어 있습니다. 참여자 0명이면 기본 출발지, 1명이면 그 사람의 출발지가 곧 최적점입니다.

### 3. 시각 계산 — `src/utils/timeUtils.ts`

`HH:mm` 문자열과 분(minute) 정수를 상호 변환하며, 자정을 넘기는 일정은 `익일 HH:mm`으로 표기합니다.

### 4. 알림 스케줄링 — `src/utils/alarmScheduler.ts`

시계를 주입(Time Injection)할 수 있는 구조입니다. 테스트에서 실제 시간이 흐르길 기다리지 않고 알림 로직을 검증할 수 있습니다.

```ts
const scheduler = new AlarmScheduler(() => mockNow, customSender);
```

## 설정 값

계산 로직에 상수를 박아 넣지 않고 `src/config/appConfig.ts` 한 곳에서 관리합니다. 설정 모달에서 값을 바꾸면 즉시 재최적화가 실행됩니다.

| 항목 | 기본값 | 설명 |
|:---|:---|:---|
| `defaultBufferMinutes` | `10` | 출발 전 여유 시간 (분) |
| `searchRadiusMeters` | `1200` | 중간지점 주변 장소 검색 반경 (m) |
| `cacheTtlMs` | `15분` | 경로 · 장소 조회 캐시 유지 시간 |
| `defaultOrigin` | 강남역 부근 | 기본 출발지 (집) |
| `defaultTransportMode` | `transit` | 기본 이동 수단 |
| `speedsKmH.walking` | `4.5` | 도보 기준 속도 (km/h) |
| `speedsKmH.transit` | `25.0` | 대중교통 기준 속도 (km/h) |
| `speedsKmH.driving` | `32.0` | 자동차 기준 속도 (km/h) |
| `peakHourCongestionMultiplier` | `1.35` | 혼잡 시간대 이동 시간 배수 |
| `maxSchedules` | `15` | 하루 최대 일정 개수 |
| `optimizationTimeoutMs` | `3000` | 최적화 타임아웃 (ms) |

## 인앱 단위 테스트

| # | 시나리오 | 검증 내용 |

| 2 | 일정 1개 단일 | 최소 단위 동선 구성 |

| 5 | 고정 + 유연 혼합 | 고정 시각 엄수 여부 |
| 6 | 참여자 1명 중간지점 | 경계 케이스 처리 |
| 7 | 참여자 5명 중간지점 | 공평성(분산) 및 성능 |
| 8 | 자정 넘김 | `익일 HH:mm` 시각 계산 |
| 9 | 출발 시각 계산식 | `도착 − 이동 − 여유` 정확성 |
| 10 | 시각 주입 알림 | 실제 대기 없이 알림 예약 검증 |
| 11 | 외부 서비스 장애 | 실패 시 폴백 동작 |
| 12 | 일정 10개 벤치마크 | 3초 이내 완료 |

## 설계 원칙

**외부 서비스 경계 분리**
`IRouteServiceProvider` 인터페이스가 지도 · 경로 · 교통 · 지오코딩 · 장소 검색을 한 겹 감쌉니다. Kakao, Naver, Google Maps, OSRM, Nominatim 어느 쪽으로 갈아타도 최적화 · 스케줄링 코드는 손대지 않습니다. 테스트에서는 같은 인터페이스를 구현한 목(mock) 프로바이더를 주입합니다.

**설정 외부화**
튜닝이 필요한 값은 모두 `appConfig.ts`에 있습니다. 알고리즘 본문에는 매직 넘버가 없습니다.

**결정적 테스트 가능성**
시계를 주입할 수 있어 시간 의존 로직도 즉시 검증됩니다.

**탄력적 폴백**
외부 조회가 실패하면 Haversine 거리와 이동 수단별 기준 속도로 이동 시간을 추정해 앱이 멈추지 않습니다.
