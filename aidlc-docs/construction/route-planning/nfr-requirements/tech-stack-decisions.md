## Q1-B 를 고른 결과 — 이동 수단 셋이 갈렸다

카카오를 고르고 나서 확인해보니, **이동 수단 세 가지가 같은 방식으로 다뤄지지 않는다.**

| 이동 수단 | 어떻게 얻나 | 실시간 교통 반영 (FR-6.1) |
|---|---|---|
| 자동차 | 카카오모빌리티 자동차 길찾기 API | **된다** |
| 도보 | 앱이 직선거리 × 평균 속도로 계산 | 안 된다 |
| 대중교통 | 앱이 직선거리 × 평균 속도로 계산 | 안 된다 |

### 왜 이렇게 됐나

| 확인된 것 | 근거 |
|---|---|
| 카카오모빌리티는 도보 · 자전거 길찾기와 지오코딩을 **제휴를 통해** 제공한다고 안내한다 | [Kakaomobility Developers](https://developers.kakaomobility.com/) |
| 카카오 로컬 REST API 는 주소 검색과 키워드 장소 검색을 제공한다 (`/v2/local/search/keyword.json` 등) | [카카오 devtalk · 로컬 API 문의 글들](https://devtalk.kakao.com/t/api-v2-local-search-keyword-json/105716) |
| 카카오맵이 2026년에 신규 API 4종을 추가했다 | [카카오 devtalk 공지](https://devtalk.kakao.com/t/api-4/150764) |

*내용은 라이선스 준수를 위해 바꾸어 적었다.*

**확인하지 못한 것** — 카카오 계열에 대중교통 이동 시간을 주는 API 가 있는지. 신규 API 4종에 그것이
들어 있는지 확인하지 못했다. 없다고 보고 Q3-B 로 갔다. 실제로 있다면 그때 창구만 갈아끼우면 된다.

도보는 제휴가 필요하다고 안내돼 있으므로, 개인이 바로 쓰기 어렵다고 보고 대중교통과 같이 자체 계산으로 다룬다.

### 이 결정이 요구사항과 어긋나는 지점

`requirements.md` FR-6.1 은 "이동 시간은 실시간 교통이 반영된 값을 사용해야 한다" 고 정했다.
**자동차만 그렇게 되고 도보 · 대중교통은 어림값이다.** 어긋나는 것을 감추지 않고 아래처럼 다룬다.

- 어림값으로 계산한 구간을 화면에 **어림값이라고 표시한다** (Q3-B 가 요구한 것)
- 창구 경계를 나눠 두어, 대중교통 API 를 얻으면 그 부분만 갈아끼운다
- 자체 계산에 쓰는 평균 속도는 설정에 둔다 (NFR-5.2)

## 자체 계산 방식 (Q3-B)

```
직선거리  =  두 좌표 사이의 대권거리 (Haversine)
이동 시간  =  직선거리 ÷ 그 수단의 평균 속도  ×  우회 계수
```

| 설정 값 | 왜 필요한가 |
|---|---|
| 도보 평균 속도 | 사람이 걷는 속도 |
| 대중교통 평균 속도 | 정류장까지 걷기 · 기다리기 · 갈아타기가 섞인 실효 속도 |
| 우회 계수 | 직선으로 갈 수 없으므로 곱한다. 실제 경로가 직선보다 긴 정도 |
| 최소 이동 시간 | 아주 가까운 곳도 0분이 되지 않게 한다 |

수치는 여기 적지 않는다. `src/domain/settings/` 에 둔다 (NFR-5.2 · U-NFR-4.1).

**이 계산은 외부를 부르지 않으므로 그대로 테스트된다.** 좌표 두 개를 넣고 분이 나오는지 보면 된다.

## Q2-A · API 키를 어떻게 다루나

```
.env.local                    ← 여기에 키를 둔다. .gitignore 에 이미 *.local 이 있다
  VITE_KAKAO_REST_KEY=...
  VITE_KAKAO_MOBILITY_KEY=...
```

| 사실 | 어떻게 다루나 |
|---|---|
| **Vite 는 빌드할 때 `VITE_` 로 시작하는 값을 결과물에 박아 넣는다** | 브라우저로 내려가는 키는 감춰지지 않는다. 이것을 감춘 척하지 않는다 |
| 서버가 없으므로 키를 대신 들고 있을 곳이 없다 | Q3-A(로컬 실행만) · Q4-A(서버 푸시 없음) 로 서버 구성 요소가 하나도 없다 |
| Q3-A 로 배포하지 않는다 | 결과물이 내 컴퓨터 밖으로 나가지 않는다. 그래서 감수한다 |
| 키가 없으면 어떻게 되나 | 창구가 실패로 다루고 자체 계산으로 넘어간다. 앱이 멈추지 않는다 |

**나중에 인터넷에 올릴 때는 이 결정을 다시 봐야 한다.** 그때는 서비스 쪽 도메인 제한(Q2-B)이나
키를 대신 들고 있는 자리가 필요해진다. `.env.local.example` 에 키 이름만 적어 두고 값은 비워 둔다.

## Q4-B · 재시도

```
외부 호출  →  실패  →  짧게 기다린 뒤 한 번 더  →  또 실패  →  캐시의 옛 값 (stale)
                                                              옛 값도 없으면  →  자체 계산
                                                              자체 계산도 못하면  →  알린다
```

| 값 | 어디에 |
|---|---|
| 재시도 전에 기다리는 시간 | 설정 |
| 한 번의 호출을 얼마나 기다리다 포기할지 | 설정 |

재시도를 한 번만 하는 이유는 NFR-1.1(3초 안) 때문이다. 여러 번 늘려가며 시도하면 3초를 넘긴다.

### Q3-B 가 실패 흐름을 바꿨다

`business-logic-model.md` 의 C-7 흐름에 **자체 계산 단계가 하나 끼어든다.**
RBR-32("옛 값도 없으면 계산할 수 없다고 알린다")가 거의 일어나지 않게 된다.
도보 · 대중교통은 애초에 외부를 부르지 않고, 자동차도 실패하면 자체 계산으로 넘어갈 수 있다.

## Q5-C · 테스트에서 외부 대신하기

| 무엇 | 어떻게 |
|---|---|
| C-2 동선 계산 | 이동 시간을 인자로 받으므로 대역을 넣는다. 외부와 무관하게 전부 검증된다 |
| 자체 계산 (도보 · 대중교통) | 외부를 부르지 않는다. 좌표를 넣고 분이 나오는지 본다 |
| 캐시 · 실패 · 재시도 흐름 | 창구 안의 "외부에 묻는 함수" 를 갈아끼운다. 실패를 일으켜 흐름을 확인한다 |
| **외부 응답을 해석하는 부분** | 저장해 둔 응답 예시를 넣어 기대한 값이 나오는지 본다 |

### 응답 해석을 따로 테스트하는 이유

여기서 틀리기 쉬운 것이 셋 있다.

| 무엇 | 왜 위험한가 |
|---|---|
| 이동 시간의 단위 | RBR 의 시각 계산은 전부 **분** 기준이다. API 가 초로 주면 60배 틀린 값이 흘러들어가 도착 불가 판정(RBR-16)이 엉뚱해진다 |
| 좌표의 순서 | 국내 서비스는 경도를 `x`, 위도를 `y` 로 쓰는 경우가 있다. 뒤바뀌면 캐시 견주기(RBR-30)까지 어긋난다 |
| 결과가 없을 때의 모양 | 빈 배열인지 필드가 없는지에 따라 RBR-38(후보 없으면 좌표를 비운다)이 제대로 도는지 갈린다 |

응답 예시는 실제로 한 번 받아 파일로 저장한다. **키를 받기 전에는 이 테스트를 만들 수 없다.**
그 자리를 비워 두고, 키를 받는 시점에 채운다.

## 폴더 짜임 — `src/gateways/` 를 새로 만든다

`schedule-core` 의 짜임에 창구 층을 더한다. `components.md` 가 예정해 둔 자리다 (C-7 · NFR-5.1).

```
src/
├── domain/
│   ├── route/                 ← 새로 만든다
│   │   ├── types.ts               R-1 ~ R-7
│   │   ├── order.ts               RBR-1 ~ RBR-7 순서 정하기
│   │   ├── schedule-times.ts      RBR-8 ~ RBR-15 시각 계산
│   │   ├── feasibility.ts         RBR-16 ~ RBR-20 도착 불가
│   │   ├── plan.ts                C-2 전체를 엮는다
│   │   └── estimate.ts            Q3-B 자체 계산 (Haversine + 평균 속도)
│   ├── settings/              ← 값을 더한다 (하루 시작 시각 · 평균 속도 · 우회 계수 …)
│   └── ...
│
├── gateways/                  ← 새로 만든다. 외부와 닿는 유일한 층 (NFR-5.1)
│   ├── mapGateway.ts              C-7 의 경계면 (인터페이스)
│   ├── kakao/
│   │   ├── localApi.ts                주소↔좌표
│   │   ├── mobilityApi.ts             자동차 길찾기
│   │   └── parse.ts                   응답 해석 — Q5-C 가 따로 테스트하는 곳
│   ├── estimateGateway.ts         자체 계산으로 답하는 창구 (도보 · 대중교통)
│   ├── compositeGateway.ts        수단에 따라 위 둘로 갈라 보낸다
│   ├── cache.ts                   R-3 캐시 · RBR-28 ~ RBR-30
│   └── retry.ts                   Q4-B
│
└── ui/
    └── RouteResult/           ← V-3
```

### 이 짜임이 지키는 것

| 요구 | 어떻게 |
|---|---|
| NFR-5.1 외부 접근 경계 분리 | `fetch` 를 부르는 곳은 `gateways/kakao/` 안에만 있다 |
| NFR-5.3 계산과 화면 분리 | `domain/route/` 는 `gateways/` 와 `ui/` 를 가져오지 않는다 |
| 서비스를 갈아끼울 수 있다 | `mapGateway.ts` 의 경계면만 지키면 `kakao/` 를 다른 폴더로 바꿀 수 있다 |
| 대중교통 API 를 나중에 얻으면 | `compositeGateway.ts` 에서 대중교통이 향하는 곳만 바꾼다 |

`compositeGateway` 가 핵심이다. 이동 수단에 따라 실제 API 와 자체 계산으로 갈라 보내는 곳이고,
Q1-B 와 Q3-B 가 만든 갈림이 여기 한 군데에 모인다.

## 사람이 준비할 것

| 무엇 | 언제 필요한가 |
|---|---|
| 카카오 개발자 계정 · REST API 키 | 주소↔좌표를 실제로 쓰려면 |
