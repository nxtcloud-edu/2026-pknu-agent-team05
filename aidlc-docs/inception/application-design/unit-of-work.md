## 단위 넷 (Q1-A)

폴더는 `aidlc-docs/construction/{단위이름}/` 이다.

| 순서 | 단위 이름 | 하는 일 | 구성 요소 | 화면 | 스토리 |
|---|---|---|---|---|---|
| 1 | `schedule-core` | 일정을 넣고 브라우저에 남긴다 | C-1 일정 펼치기 · C-5 보관소 · C-6 설정 | V-1 하루 보기 · V-2 일정 상세 · V-7 하루 설정 · V-9 데이터 관리 | S-1, S-2, S-3, S-4, S-5, S-6, S-16 |
| 2 | `route-planning` | 실제 이동 시간을 받아 동선을 추천한다 | C-2 동선 계산 · C-7 지도 창구 | V-3 동선 결과 | S-7, S-8, S-9, S-10 |
| 3 | `departure-alarm` | 출발 시각을 계산해 알림을 걸어둔다 | C-4 출발시각 계산과 알림 예약 | V-8 알림 상태 | S-15 |
| 4 | `meetup-midpoint` | 약속의 중간지점과 만남 장소 후보를 낸다 | C-3 중간지점 계산 · C-8 장소 창구 | V-4 약속 · V-5 중간지점 결과 · V-6 장소 후보 | S-11, S-12, S-13, S-14 |

**`departure-alarm` 을 끝낸 시점이 "돌아가는 앱"의 기준이다** (execution-plan Q5-C).
일정을 넣고, 동선을 받고, 출발 시각에 알림이 온다. `meetup-midpoint` 는 그 위에 얹는다.

## 단위 사이 의존

```
schedule-core ──┬──▶ route-planning ──▶ departure-alarm
                │           ▲
                │           │ 장소가 확정되면 다시 계산한다
                └──▶ meetup-midpoint ─┘
```

| 단위 | 없으면 못 서는 것 | 왜 |
|---|---|---|
| `schedule-core` | 나머지 전부 | 계산할 일정 자체가 없다 |
| `route-planning` | `departure-alarm` | 출발 시각은 동선 결과의 도착 시각과 이동 시간에서 나온다 |
| `route-planning` | `meetup-midpoint` 의 S-14 | 확정된 장소를 동선에 얹는 계산이 필요하다 |
| `departure-alarm` | — | 뒤에 오는 단위가 이것에 의존하지 않는다 |

`meetup-midpoint` 를 `departure-alarm` 뒤에 둔 이유는 의존이 아니라 Q5-C 다. 핵심 흐름을 먼저 잇는다.

## 경계면 — 무엇을 넘기나 (Q2-A)

아래는 **의미**를 못 박은 것이다. 이름 · 타입 · 자료 구조는 CONSTRUCTION 01 기능 설계에서 정한다.
뒤 단위를 만들 때 앞 단위 코드를 다시 읽지 않아도 되도록, 넘기는 것의 내용을 여기 적어 둔다.

### 경계 1 · `schedule-core` → `route-planning`

```
넘기는 것 ①  그날의 일정 목록 (C-1 이 펼친 결과)
   일정마다
     · 무엇을 하는 일정인지 (제목)
     · 어디인지 (좌표. 주소만 있으면 좌표로 바꾼 값)
     · 얼마나 머무는지
     · 시간 고정형인지 유연형인지
     · 고정형이면 도착해야 하는 시각
     · 이동 수단 (고르지 않았으면 기본값이 채워진 상태)
     · 완료 표시 여부 → 동선 계산에서 빠질 것인지
     · 사용자가 순서를 손으로 고정했는지, 고정했다면 몇 번째인지
     · 약속인지 여부 (meetup-midpoint 가 쓴다)

넘기는 것 ②  하루 설정
     · 하루의 출발지 (좌표)
     · 마지막 도착지 (좌표. 비어 있을 수 있다)

넘기는 것 ③  설정 값
     · 기본 이동 수단
     · 이동 시간 캐시 유지 시간
```

**약속** — 목록은 이미 반복 규칙과 예외가 합쳐진 상태다. `route-planning` 은 반복 규칙을 모른다.
완료 표시된 일정도 목록에 남아 있지만 "빠질 것"으로 표시돼 있다. 걸러내는 일은 `route-planning` 이 한다.

### 경계 2 · `route-planning` → `departure-alarm`

```
넘기는 것 ①  동선 결과
     · 확정된 순서
     · 구간마다
         · 어느 일정으로 가는 구간인지
         · 목적지가 어디인지 (알림 문구에 들어간다)
         · 출발 시각
         · 도착 시각
         · 이동 시간
         · 이동 수단
         · 이 이동 시간이 최신인지, 아니면 예전 값을 쓴 것인지

넘기는 것 ②  또는 도착 불가 경고
     · 어느 일정에 닿을 수 없는지
     · 몇 분 모자라는지
     ( 이 경우 departure-alarm 은 알림을 걸지 않는다 )
```

**약속** — `departure-alarm` 은 이동 시간을 스스로 구하지 않는다. 여기서 받은 값만 쓴다.
이동 시간이 바뀌면 `route-planning` 이 결과를 다시 내고, `departure-alarm` 은 그 결과로 알림을 다시 잡는다 (FR-6.2).

### 경계 3 · `schedule-core` ↔ `meetup-midpoint`

```
schedule-core → meetup-midpoint
     · 약속으로 지정된 일정 하나
     · 그 약속에 딸린 참여자들 { 이름 · 출발지 좌표 · 이동 수단 }
     · 설정 값 { 장소 검색 반경 · 중간지점 후보 개수 }

meetup-midpoint → schedule-core
     · 확정된 약속 장소 (좌표와 이름)
     · 참여자 추가 · 수정 · 삭제
```

**약속** — 참여자를 보관하는 곳은 `schedule-core` 의 C-5 다. `meetup-midpoint` 는 자기 보관소를 만들지 않는다.
`components.md` C-5 에 참여자(⑤)가 이미 예정돼 있으므로, `meetup-midpoint` 를 만들 때 그 자리를 채우는 것은 되돌아갈 일이 아니다 (아래 Q4-C 기준 참고).

### 경계 4 · `meetup-midpoint` → `route-planning`

```
넘기는 것
     · 약속 장소가 확정됐다는 사실
     ( route-planning 이 그 일정의 장소를 새로 읽어 동선을 다시 낸다 )
```

**약속** — 장소가 확정되면 동선과 출발 시각이 모두 다시 계산된다. `meetup-midpoint` 는 다시 계산해 달라고 알리기만 하고, 계산은 `route-planning` 이 한다 (S-14).

## 단위마다 완료 기준 (Q3-B)

**계산 단위 테스트가 통과하면 그 단위는 끝난 것으로 본다.** 화면 확인은 CONSTRUCTION 06 에서 몰아서 한다.

| 단위 | 통과해야 하는 것 |
|---|---|
| `schedule-core` | C-1 일정 펼치기 — 반복 규칙이 해당 요일에 나타남 · `건너뜀` 예외로 빠짐 · `고침` 예외로 바뀐 값이 들어감 · 완료 표시가 "빠질 것"으로 표시됨 · 일정 0개 |
| `route-planning` | C-2 동선 계산 — 유연형만 재배치됨 · 고정형 순서와 시각 불가침 · 손으로 고정한 자리 유지 · 도착 불가면 순서 대신 경고 · 일정 0개 1개 · 자정 넘김<br>C-7 지도 창구 — 캐시가 외부 호출을 줄임 · 외부 실패 시 이전 값과 "최신 아님" 표시 |
| `departure-alarm` | C-4 — `도착 시각 − 이동 시간 − 여유 시간` 이 출발 시각이 됨 · 여유 시간 설정 반영 · 이동 시간이 바뀌면 다시 잡힘 · 완료된 일정의 알림이 걷힘 · 도착 불가 경고를 받으면 알림을 걸지 않음<br>지금 시각을 주입해 검증한다 (실제 시간을 기다리지 않는다) |
| `meetup-midpoint` | C-3 중간지점 — 편차가 임의로 고른 다른 지점보다 작음 · 참여자별 이동 수단 반영 · 참여자 1명<br>C-8 장소 창구 — 반경 안에 결과가 없을 때 |

계산 요소는 외부를 직접 부르지 않으므로, 이동 시간과 장소 목록을 대역으로 넣어 검증한다 (NFR-3.1).

### 완료 기준에 넣지 않은 것

Q3-B 를 고른 결과다. 아래는 CONSTRUCTION 06 빌드와 테스트에서 한 번에 확인한다.

- 화면 V-1~V-9 가 제대로 그려지는지 (Q5-A · Q3-B)
- 성능 3초 (NFR-1.1, NFR-1.2)
- 탭이 닫힌 상태에서 알림이 실제로 오는지 (FR-5.2) — 브라우저에서 손으로 확인해야 한다
- 알림 권한이 거부된 상태의 안내 (FR-5.5)

## 앞 단위를 고쳐야 할 때 (Q4-C)

경계가 애매하지 않도록 기준을 못 박는다.

### 그 자리에서 고친다

| 경우 | 예 |
|---|---|
| 앞 단위의 버그를 발견했다 | `route-planning` 을 만들다 C-1 이 완료 표시를 잘못 다루는 것을 발견 |
| 설계에 이미 자리가 예정돼 있어 채우는 것이다 | `meetup-midpoint` 에서 C-5 에 참여자를 저장 — `components.md` C-5 ⑤ 에 예정돼 있다 |
| 기존 동작을 깨지 않고 덧붙이는 것이다 | `departure-alarm` 이 쓸 설정 값(여유 시간)을 C-6 에 추가 |

고친 뒤 **그 단위 폴더의 `code/` 요약에 무엇을 왜 고쳤는지 한 줄 남긴다.**

### 되돌아간다

| 경우 | 예 |
|---|---|
| 확정된 요구사항이나 `components.md` 의 경계와 어긋나게 된다 | 일정을 날짜별로 묶어 저장하는 편이 맞다는 결론 — Q4-C 로 확정한 데이터 구조를 뒤집는다 |
| 앞 단위의 완료 기준이 더 이상 성립하지 않는다 | C-1 의 펼치기 테스트를 통과하지 못하게 구조를 바꿔야 한다 |
| 계산이 화면으로, 또는 외부 호출이 계산으로 새어 나가야 한다 | NFR-5.1 · NFR-5.3 을 어기게 된다 |

되돌아가는 경우는 `mistakes.md` 에 기록한다 (§5 의 2번 — 확정된 설계와 다르게 만들어 되돌렸을 때).

### 단위마다 STEP 02 에서 고를 것

스택을 고르는 곳은 여기 한 군데뿐이다. 단위마다 새로 필요한 것만 덧붙인다.

| `schedule-core` | 언어 · 프레임워크 · 브라우저 저장 방식 · 테스트 도구 · 빌드 방식 |
